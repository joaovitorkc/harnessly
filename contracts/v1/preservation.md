# Preservation and ownership v1

Harnessly modifies repositories it does not own. Preservation is therefore
part of correctness.

## Ownership classes

- **Unmanaged:** existing user content. Readable as evidence; never replaced.
- **Create-only:** an absent path proposed by a workflow. Existing bytes equal
  to the complete planned content are `NO_CHANGE`; any other collision stops
  apply.
- **Managed block:** a marked section in shared Markdown or text.
- **Structural merge:** selected keys/nodes in parsed JSON, YAML, TOML, XML, or
  package manifests, or exact entries in declared line-oriented configuration
  such as `.gitignore`. It is not a source-code editing strategy.
- **Source patch:** the smallest syntax-aware or contextual patch to declared
  source/test paths, guarded by the assessed preimage digest.
- **Owned file:** generated by Harnessly with a stable provenance marker.
- **Generated adapter:** derived from one canonical source and checked for
  byte-level parity.

Managed text uses stable markers:

```text
<!-- harnessly:start <id> -->
...
<!-- harnessly:end <id> -->
```

A workflow must find zero or one valid block. Multiple, nested, mismatched, or
edited markers are a conflict.

Owned Markdown starts with:

```text
<!-- harnessly:owned workflow=<slug> version=<semver> -->
```

Other text formats use the equivalent native comment. The marker proves
provenance, not permission to overwrite: the workflow also records the file's
SHA-256 during assessment and rechecks that same digest immediately before the
write.

A source patch must identify the exact file and construct being changed, record
the preimage SHA-256, recheck it before writing, and stop if context is
ambiguous. Broad search/replace is forbidden. The resulting diff must contain
only the declared behavior change and must pass the focused parser/compiler
and tests; otherwise report `PARTIAL` or `FAILED`.

## Preconditions

Before each write, re-read the path and compare it to the assessed state. Stop
on drift. An owned file without the expected workflow/version marker is
unmanaged. A changed assessment digest invalidates the write.

## Repository boundaries

- Do not traverse `.git/`.
- Treat nested Git roots as independent repositories.
- Do not create nested repositories or change remotes.
- Do not follow a symlink outside the authorized root.
- Do not copy or move product code into `orchestrator/`.

## Conflict behavior

Show the existing path, intended owner, proposed strategy, and smallest safe
manual resolution. Do not rename the user's file, create a surprising sibling,
or overwrite it to “keep going.”

## Rollback

For R1/R2 changes, the pre-apply Git diff is the rollback reference. Harnessly
does not run destructive Git restore commands. The report lists created and
modified paths so the user can review or revert them with their normal tools.
